Preprocesamiento de la base de datos de Hogar

Bitácora del TFM de pricing de Hogar: modelos de frecuencia y severidad (GLM y XGBoost) sin y con variables de contexto por código postal. Aquí se explica, en el orden en que se hace, cada paso del preprocesamiento en R: qué significa cada variable, qué se encontró al revisarla, cómo se tratan sus nulos y qué transformación se le aplica.

Confidencialidad

La base de datos no se publica ni se sube al repositorio. Esta página solo contiene el código y la descripción de las variables; los resultados de la revisión se describen de forma cualitativa, sin cifras ni registros de la base.

Mapa

El proceso, en orden

El preprocesamiento se hace una variable cada vez: primero se mira (tipo, nulos, valores raros, distribución) y solo después se transforma. Nada se convierte en bloque, porque un cambio masivo esconde problemas distintos en cada variable.

Contexto

Para qué se preprocesa

  • El objetivo es predecir la prima pura (coste esperado por póliza y año) como frecuencia × severidad.
  • Las variables de contexto por código postal son predictores que se añaden para predecirla mejor; no son la prima pura.
  • "Mejorar el modelo" significa predecir mejor fuera de muestra (test temporal y validación cruzada por zona).
  • Diseño 2 × 2: GLM base, GLM con contexto, XGBoost base y XGBoost con contexto.

Un preprocesamiento descuidado rompe esa comparación: un tipo mal leído, un nulo que en realidad es una categoría o una variable que contiene el futuro (fuga) cambian el resultado más que el propio modelo.

Paso 0 · hecho

Cargar la base en R

R · Preprocess.R
library(tidyverse)
library(readxl)

readxl::excel_sheets("Datos//base de datos de hogar.xlsx")   # hojas del Excel
mi_base <- read_excel("Datos//base de datos de hogar.xlsx")  # lee la primera hoja
head(mi_base); tail(mi_base); dim(mi_base)
df_hogar <- mi_base   # copia de trabajo: mi_base queda intacta
  1. excel_sheets lista las hojas para saber cuál leer; los datos están en la primera.
  2. read_excel deduce el tipo de cada columna mirando sus valores. Si una sola celda no encaja, toda la columna se lee como texto: por eso el paso 1 revisa los tipos.
  3. head, tail y dim comprueban que se ha leído entera y sin filas basura al principio o al final.
  4. Se trabaja sobre df_hogar para poder comparar siempre con el original.
Paso 1 · hecho

Revisar el tipo de cada variable

R
str(mi_base)   # tipo de cada columna y primeros valores

Qué se encontró. Varios importes (primas y capitales) se leen como texto, las categóricas como texto y CANAL como número aunque es un código. FECHAALTA se lee como fecha-hora.

La decisión de este paso es la lista de tareas del paso 2: cada variable con un tipo que no corresponde a su significado se revisa por separado.

Paso 2

Variable a variable

Para cada variable se sigue el mismo patrón: mirar (tipo, valores crudos, nulos), comprobar qué se perdería al transformar, transformar y verificar que no ha aparecido ningún nulo nuevo.

2.1 FECHAALTA hecho

R
class(df_hogar$FECHAALTA)        # qué tipo ha leído readxl
head(df_hogar$FECHAALTA)         # valores crudos
sum(is.na(df_hogar$FECHAALTA))   # nulos antes de convertir

df_hogar <- df_hogar %>%
  mutate(FECHAALTA = as.Date(FECHAALTA))

class(df_hogar$FECHAALTA)        # ahora "Date"
sum(is.na(df_hogar$FECHAALTA))   # no debe subir
range(df_hogar$FECHAALTA, na.rm = TRUE)
  1. class y head: antes de convertir hay que saber cómo viene. Se esperaba un número de serie de Excel, pero readxl ya la había leído como fecha-hora (POSIXct).
  2. Por eso no se usa as.Date(x, origin = "1899-12-30"): sobre una fecha-hora, as.numeric da segundos desde 1970 y el resultado serían fechas absurdas.
  3. sum(is.na(...)) antes y después: si el número de nulos sube, la conversión ha perdido datos.
  4. mutate(... = as.Date(...)) quita la hora y la zona horaria; para una póliza basta el día.
  5. range comprueba que las fechas tienen sentido para la cartera.

Resultado. Tipo fecha, sin nulos antes ni después, y un rango de altas coherente. La variable queda lista; servirá para derivar la exposición y el corte temporal.

2.2 PRNETA11 en curso

a) Tipo. Se lee como texto, así que summary no da cuartiles y ggplot no puede dibujar un histograma. Antes de convertir hay que saber por qué es texto.

R
head(df_hogar$PRNETA11, 20)      # ¿coma decimal?, ¿símbolos?
sum(is.na(df_hogar$PRNETA11))

num_prueba <- suppressWarnings(as.numeric(df_hogar$PRNETA11))
no_convertibles <- df_hogar$PRNETA11[is.na(num_prueba) & !is.na(df_hogar$PRNETA11)]
length(no_convertibles)
head(sort(table(no_convertibles), decreasing = TRUE), 20)
  1. num_prueba intenta la conversión sin tocar df_hogar.
  2. no_convertibles son los valores que fallarían (dan nulo) sin ser nulos de origen: exactamente lo que un as.numeric directo convertiría en nulo sin avisar.
  3. table ordenada enseña qué textos raros hay y cuántas veces, si los hubiera.

Resultado. Formato numérico normal con punto decimal, sin nulos y sin ningún valor no convertible. La conversión es segura.

b) Conversión y distribución.

R
df_hogar <- df_hogar %>%
  mutate(PRNETA11 = as.numeric(PRNETA11))

summary(df_hogar$PRNETA11)
sum(df_hogar$PRNETA11 <= 0)                                    # primas a 0 o negativas
ggplot(df_hogar, aes(PRNETA11)) + geom_histogram(bins = 50)
ggplot(df_hogar, aes(y = PRNETA11)) + geom_boxplot()

Resultado. Sin nulos ni primas nulas o negativas. El cuerpo de la distribución es estrecho, pero hay una cola derecha muy larga: el máximo es decenas de veces la mediana y el histograma apenas deja ver nada fuera del primer tramo.

c) Análisis de la cola (pendiente de ejecutar). Una prima alta no es un error por sí misma: una vivienda grande o con capitales altos paga más. Antes de recortar o excluir se mira si la cola se explica por otras variables.

R
quantile(df_hogar$PRNETA11, c(.90, .99, .999, .9999, 1))   # dónde se dispara la cola
sum(df_hogar$PRNETA11 > 500)
sum(df_hogar$PRNETA11 > 1000)
df_hogar %>%
  arrange(desc(PRNETA11)) %>%
  select(PRNETA11, TVIVIENDA, M2, CAP_VIVIENDA, CAP_ENSERES, EDAD, NUMSINIESTROS_TOTAL) %>%
  head(10)

Opciones según lo que salga: dejarla como está (prima legítima), poner un tope (capping) o excluir solo los casos con error evidente. Como PRNETA11 es la prima cobrada, sirve para el loss ratio y no es el objetivo del modelo, lo que reduce el impacto de los extremos.

2.3 y siguientes pendiente

Mismo patrón, en este orden:

  1. PRNETA12: igual que PRNETA11; además, comparar ambas para aclarar qué representa cada una.
  2. CAP_VIVIENDA, CAP_ENSERES, CAP_RCGENERAL: tipo, ceros (¿cobertura no contratada o dato ausente?) y extremos.
  3. COSTE y SINIESTRO: coherencia entre ambas (coste positivo solo si hay siniestro) y cola de la severidad.
  4. ULT_REFORMA: unificar las marcas de "sin informar" y decidir si se usa.
  5. HPOL_MOT_FIN: el vacío pasa a la categoría "sin baja".
  6. Categóricas (TVIVIENDA, INQPRO, HABSE, FPAGO, cliente descuento, CANAL): a factor con nivel de referencia para el GLM.
  7. Numéricas (EDAD, M2, ANO_CONSTR, anti_poliza, mes): nulos, rangos imposibles y extremos.
  8. Históricos de siniestros (NUMSINIESTROS_TOTAL, SS_*, REHUSADOS): comprobar si la suma por garantías cuadra con el total y decidir su uso tras fijar el corte temporal.

Antes de modelar

Avisos abiertos

Fuga de información

SINIESTRO y COSTE son del periodo que se quiere predecir; NUMSINIESTROS_TOTAL y los SS_* son históricos y pueden incluir ese mismo periodo. No se usan como predictores hasta fijar el corte temporal.

Sin exposición explícita

No hay columna de exposición. Se derivará de FECHAALTA, mes y anti_poliza para el offset log(exposición) del GLM de frecuencia.

Sin código postal

Entre las 33 columnas no aparece el código postal, que es la clave para unir las variables de contexto. Hay que confirmar si existe en otra fuente.

Variables sin descriptivo

PRNETA11, PRNETA12 y ULT_REFORMA no tienen descripción; los significados de SS_*, REHUSADOS, mes y anti_poliza se deducen del nombre. Conviene confirmarlos con el autor de la base.
